1. 문서 메타데이터와 근거 범례

  • 프로젝트: PokerStrike(패키지명 card-defense), 버전 0.4.0, Phaser 3.60 기반 웹/Electron 게임.
  • 근거 표기: [사실] = package.json·파일 목록에서 직접 확인, [제안] = 파일명·구조 기반 추론(내용 미열람).
  • 이번 문서는 파일 읽기 권한 제한으로 기획서 본문을 직접 인용하지 못해, 대부분의 세부 규칙/수치는 [제안]으로 표기함.

2. 문제 정의

  • [사실] docs/next_improvement_instruction.md, docs/persona_playtest_feedback.md 파일이 존재해 사용자 피드백 기반 개선 작업이 진행 중임을 시사.
  • [제안] 카드 뽑기와 방어 로직을 결합한 '카드 디펜스' 장르 특성상, 초심자가 포커 족보와 디펜스 타이밍 판단을 동시에 학습해야 하는 진입장벽이 문제로 추정됨.

3. 한 줄 피치와 제품 포지셔닝

  • [제안] "포커 족보로 적을 막아내는 카드 디펜스" — 포커 핸드 평가(HandEvaluator)와 전투(CombatManager) 모듈이 결합된 구조에서 유추.
  • 포지셔닝: 캐주얼 카드 배틀 + 타워디펜스 하이브리드, PC(Electron) 단일 실행 파일 배포.

4. 주 페르소나

  • [제안] 이름: 김도현, 32세, 회사원(IT 업계 사무직), 퇴근 후 20~30분 짧은 세션으로 캐주얼 게임을 즐기는 라이트 게이머.
  • 포커 룰은 어느 정도 알지만 복잡한 전략 게임에는 시간을 쓰기 부담스러워하며, 짧고 반복 가능한 판을 선호함(파일 목록상 근거 부족으로 페르소나 상세는 가설).

5. 디자인 기둥과 핵심 재미

  • [제안] 족보 조합의 손맛: 카드 조합을 완성했을 때의 타격감(콤보 피드백 관련 스펙 문서 2026-06-26-combo-impact-feedback-design.md 존재로 뒷받침).
  • [제안] 경제/성장 관리: EconomyManager.test.js 존재로 자원 관리 시스템이 핵심 루프의 일부임을 시사.

6. 핵심 루프

유저가 선택을 하면 결과가 되고, 그 결과 때문에 다시 선택을 한다.

카드를 뽑는다 → 포커 족보를 조합한다 → 조합된 핸드로 적을 공격/방어한다 → 자원을 획득해 덱/능력을 강화한다 → 다시 카드를 뽑는다.
- [사실] Deck, HandEvaluator, CombatManager, EconomyManager 각 모듈의 테스트 파일 존재가 이 순환 구조를 뒷받침함.

7. 최초 30초 플레이 흐름

  • [제안] 실행 → 스플래시 화면(docs/splash.png 존재) → 메인 메뉴 → 첫 판 시작, 초기 카드 5장 배분 → 첫 족보 조합 시도.
  • 세부 타이밍·튜토리얼 텍스트는 미확인이라 구체 수치 제시 불가.

8. 게임 규칙과 승패 조건

  • [제안] 포커 족보(원페어~로열스트레이트플러시 등급)를 조합해 적 유닛에 대응, HandEvaluator 모듈이 족보 판정 담당.
  • [제안] CombatManager가 전투 결과(승/패, 데미지) 처리, 자원이 고갈되거나 방어선이 뚫리면 패배로 추정됨(세부 승패 수치는 문서 미열람으로 확정 불가).

9. 콘텐츠, 진행, 성장, 경제 구조

  • [사실] EconomyManager 테스트 존재로 재화/자원 관리 시스템이 구현되어 있음.
  • [제안] 아트 리소스 목록(PokerStrike_아트_리소스_목록.md)과 UI 리소스 목록 문서가 존재해 카드/유닛 비주얼 콘텐츠가 체계적으로 관리되고 있으나, 진행 단계 수·성장 트리 구조는 본문 미열람으로 특정할 수 없음.

10. MVP 가설과 검증 방법

  • 가설1: 포커 족보 조합 자체가 별도 학습 없이도 직관적으로 재미있을 것이다 → 플레이테스트 피드백 문서(persona_playtest_feedback.md)를 통한 정성 검증.
  • 가설2: 경제(EconomyManager) 성장 루프가 반복 플레이 동기를 유지시킬 것이다 → 재플레이 의향 설문으로 검증 제안.
  • 검증 방법은 기존 persona_playtest_feedback.md 문서 활용을 전제로 하되, 본문 미열람으로 실제 수행 여부는 확인하지 못함.

11. 레퍼런스별 핵심 행동 단계 수와 적용 교훈

  • [사실] docs/PokerStrike_레퍼런스_플레이예시_구버전2.png, docs/assets/PokerStrike_레퍼런스_ui-kit-v1.png 레퍼런스 이미지 파일 존재.
  • [제안] 레퍼런스 핵심 행동 단계(예: 카드 선택→조합 확인→공격 실행 3단계)는 이미지 내용 미열람으로 구체화 불가하며, UI 킷 레퍼런스는 카드 배치/HUD 레이아웃 참고용으로 추정됨.

[제안] 적용 교훈은 카드 선택 → 조합 확인 → 공격 실행의 3단계마다 현재 족보와 실행 후 기대 효과를 끊김 없이 갱신하는 것이다.

12. 수치 KPI와 측정 방법

  • 제안 KPI1: 첫 세션 완료율 70% 이상 — 측정: 첫 판 시작 후 종료(승/패)까지 도달한 세션 비율 로깅.
  • 제안 KPI2: 재플레이율(D1) 30% 이상 — 측정: 실행 파일 재실행 또는 신규 게임 시작 이벤트 카운트.
  • 실제 계측 로직 존재 여부는 이번 세션에서 코드 미열람으로 확인 불가하여 목표치는 검증 대상 가설로 표기함.

13. UI, HUD, 컨트롤

1) 로딩/스플래시 상태 — docs/splash.png 참고.
2) 메인 메뉴 상태.
3) 인게임 플레이 상태(카드 핸드, HUD 자원 표시).
4) 결과(승/패) 상태.
5) 설정/일시정지 상태.
- 구체 레이아웃은 PokerStrike_UI_리소스_목록.md에 정리되어 있으나 본문 미열람으로 세부 좌표·요소는 명시 불가.

14. 로딩·빈 상태·에러·100개 이상 데이터·3배 긴 텍스트 대응

  • [제안] 덱에 카드가 100장 이상 누적되는 경우 UI 리소스 목록 문서 기준 스크롤/페이지네이션 대응이 필요할 것으로 추정되나, 실제 처리 로직은 코드 미열람으로 확인되지 않음.
  • 긴 텍스트(카드 이름, 족보명) 다국어 대응 여부도 문서 미열람으로 확인 불가.

15. 접근성

  • [제안] 카드 게임 특성상 색맹 사용자를 위한 카드 무늬(스페이드/하트/다이아/클로버) 식별 보조가 필요할 것으로 추정되나, 현재 구현 여부는 코드 미열람으로 확인되지 않음.
